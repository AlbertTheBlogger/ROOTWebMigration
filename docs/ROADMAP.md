# ROOT 网页版：逆向研究、开发与部署路线

规划日期：2026-11-08。本文是后续实施计划，不表示尚未开发的功能已经完成。现有公网服务保留规则验证版定位。

## 1. 目标与当前基线

目标：浏览器访问、独立账号、房间号及可选密码、每局独立玩家名、服务器裁决和存档，逐步覆盖目标数字版实际具有的玩法及内容。

当前事实：

- 安装包为 Unity 2022.3.21f1 / IL2CPP metadata v29；没有原工程或 C# 源码。
- 检查记录包含 177 个文件、118 个 AssetBundle 和核心文件指纹。
- 现有程序完成账号、两人房间、部分猫 / 鹰规则及服务器保存；使用测试地图与花色测试牌。
- 29 项自动化测试通过；真实浏览器点击验收尚未完成，不能将测试数量视为原规则覆盖率。
- 服务部署在 Ubuntu 22.04，使用 Node 24.11.1、SQLite、SSE、systemd。
- 测试入口 http://103.236.93.55:233 ，公网 233 → 内部 80；SSH 公网 55215 → 内部 22。
- 代码 `/opt/woodland-rooms`，数据 `/var/lib/woodland-rooms`；当前没有 HTTPS、自动发布流水线或多实例能力。

实施主线是依据原版行为和规则重实现。逆向用于建立证据、提取结构化数据及定位差异；是否能恢复有用的方法体，必须先通过样本验证。原客户端可能不包含原服务端的完整实现，不能据客户端文件推断后端代码可恢复。

## 3. 逆向研究计划

### R1：建立可重复研究环境

- 在 `research/` 下建立工作区；原安装目录只作为输入，输出与其分开。
- 保存工具来源、版本 / 提交号、运行参数、输入哈希、导出日志与失败记录。
- 阅读 Addressables catalog、link.xml、localization、资源关联，建立 bundle → 对象 → 功能索引。
- 优先索引地图、卡牌、阵营板、文本与游戏状态；无需一次导出全部音频和动画。

交付：`research/manifest.json`、`research/content-matrix.csv`、工具兼容性记录。以上是待创建产物，不是已完成项。

### R2：先做三类小样

1. **地图样本**：定位一个正式地图，记录道路、河流、森林邻接、花色、建筑位、废墟和角落信息；图像坐标与逻辑拓扑分开。
2. **卡牌样本**：定位至少一张物品制作牌、一张伏击牌和一张持续效果牌，核对 ID、花色、数量、成本、效果及本地化文本。
3. **流程样本**：选猫侯国一次建造及一次带中断的战斗，定位相关状态 / 命令 / 校验类型，并用离线原版行为核对。

候选工具：AssetRipper 用于浏览和导出 Unity 资源；UnityPy 用于将已确认对象批量转成结构化数据；Cpp2IL 用于 IL2CPP 类型和方法研究。Il2CppDumper 可作为类型结构索引的备选，但其 README 列出的支持范围截至 Unity 2022.2，目标是 2022.3.21f1，不能预先承诺兼容。

Il2CppDumper 的 DummyDll 不包含原方法代码；Cpp2IL 也是持续开发中的工具，恢复结果需要核对，不能直接当作可编译原工程。工具能力与来源见本文末尾链接。

**研究停止条件**：首轮安排约 8–16 小时有效研究工作量作为探索上限，属于规划估计。若方法恢复不能稳定产出可验证证据，就保留类型 / 数据分析结果，以规则书与可观察行为推进重实现；不让“恢复完整源码”无限阻塞开发。

### R3：规则证据与差异表

每条规则记录：稳定规则 ID、原版版本、规则书条目、数据来源、观察步骤、期望结果、当前实现状态及测试用例。

证据区分：已提取的数据、已观察的行为、工具推断、尚未验证的假设。程序与公开规则书有差异时，记录后选定该规则集的目标行为，不在代码中悄悄混用版本。

原版行为样本优先通过本地 / 离线对局采集。新的网页联机协议自行设计；不需要复刻原 Steam 或其他在线服务协议。程序集名称只能提示研究方向，不能证明原联机完全依赖 Steam。

### R4：存档与表现资源

- 原版存档导入独立于新网页存档：先确认文件位置、格式、版本和状态完整性，再决定能否映射；目前不承诺兼容。
- 可先导出小样验证纹理、透明图集、模型和骨骼是否可被网页使用，不能把 Windows AssetBundle 当成网页可直接加载的资源。
- 建立资源来源、用途和允许使用范围清单；研究导出物与实际上线资源目录分开管理。
- 首版正式玩法可采用清晰的 2D 棋盘与资源图集；3D 模型、骨骼动画、镜头和音效作为后续表现迭代。

## 4. 后端与规则开发

### D1：先解决现有结构的扩展限制

现有规则引擎多处写死猫 / 鹰与两名玩家。先逐步拆分为：

```text
backend/
  auth/                 # 账号、会话
  rooms/                # 房间、席位、本局玩家资料
  persistence/          # 迁移、事务、快照、命令与事件
  rules/
    core/               # 棋盘、棋子、战斗、制作、胜利条件
    effects/            # 触发、选择和继续执行
    factions/           # 各阵营规则
    versions/           # 规则集注册与旧版本读取
  data/                 # 正式地图、卡牌和阵营板数值
```

渐进拆分，不先进行与交付无关的大规模框架重写。地图 / 牌库 / 内容包采用独立 ID、schema 和完整性校验，移出过程代码。

### D2：持久化的结算队列

将单一 `pending` 扩展为可恢复的效果队列。每个待选择项具有 `choiceId`、执行玩家、合法选项、关联效果、继续位置与状态版本。

以一次战斗验证：发起 → 伏击选择 → 反伏击选择 → 骰子与卡牌效果 → 损失及触发效果 → 医院等后续处理 → 继续原行动。具体先后顺序必须依据选定规则版本逐项测试，不预设所有触发都服从同一固定顺序。

任何需要玩家决定的位置都保存到数据库；重启不能跳过选择、重复执行效果或重新掷骰。断线期间不默认代替玩家做不可逆选择，后续另行定义超时策略。

### D3：命令、随机结果和隐私

- 保留唯一命令 ID、房间 / 对局版本检查及事务提交。
- 为对局单独记录命令、随机结果、规则事件、规则版本和状态版本；当前快照仍用于快速恢复。
- 重放使用已记录的随机结果，不重新调用随机数；私有洗牌与抽牌信息仅存后端，不进入公开日志。
- 针对手牌、支持者、阴谋等逐类实现玩家视图；观战 / 回放如未来开放，也需独立投影。
- 后端提供当前合法操作和选择选项；前端高亮与提示基于这些结果，减少两端各维护一份规则。
- 保存完整事件记录供排错；当前截断到 80 条的展示日志不能承担完整重放职责。

### D4：内容实施顺序

1. 秋季正式地图、所选基础牌库、物品供应和完整标准开局。
2. 共同规则：制作、持续效果、伏击、损失顺序及即时胜利结算。
3. 猫：开局选择、制作阶段、医院及行动组合边界；鹰：初始领袖选择、完整领袖能力、政令和动乱边界。
4. 联盟：支持者、同情、戒严、愤怒、起义、军官与基地移除。
5. 游侠：森林、物品、损坏 / 耗尽、任务、关系、援助、战斗和胜利方式。
6. 核验扩展内容后接入河岸 / 蜥蜴与地底 / 乌鸦；百兽 / 守护者作为完整主里程碑，分别实现再验证相互作用。
7. 额外地图、牌库、雇佣兵、AI / 单人挑战按实际目标内容单独验收。

基础四阵营先支持 2–4 人；扩展到更多席位时按规则组合和地图限制验证，不直接把人数上限改成 6 就视为支持六人游戏。

### D5：房间和账号完善

明确房间、席位和单局玩家身份的区别。玩家名复制到每局记录，下一局改名不改变历史；掉线保留席位，房主离线 / 离开、重连、多设备登录、认输及下一局流程均有明确策略。

房间密码继续只存哈希，不作为会话凭据。密码重置、会话管理和邀请链接按测试反馈补充；不默认引入邮件服务。旁观、聊天和回放界面放在核心对局稳定后。

## 5. 前端计划

- 拆分登录、大厅、房间、棋盘、玩家板、卡牌、选择对话框和日志；保持 API 为独立边界。
- 替换手填林地编号与木材编号：点击棋子 / 目标、高亮合法移动、数量选择、木材分配预览。
- 显示动作成本、得分变化、谁在决定下一步、操作失败原因及连接状态；在提交前保留用户选择，避免推送刷新使表单丢失。
- 实现卡牌详情、制作条件、阵营板进度和移动端手牌区域；动画以服务器已确认事件为输入。
- 前端动画中断、刷新或跳过时不影响规则进度。旧请求超时后先核对命令是否已提交，再决定是否重试。
- 先通过双浏览器完整双人对局，再进行四窗口 / 四设备和移动端验收。自动化覆盖注册、建房、入房、准备、关键中断、刷新恢复及自然结束。

## 6. 测试与验收

测试重点是规则覆盖和行为证据，不设单纯的测试数量目标。

| 维度 | 必须覆盖的内容 |
| --- | --- |
| 数据 | 地图邻接对称、建筑位 / 废墟、牌库数量和类型、棋子总供应 |
| 共同规则 | 统治平局、移动、制作成本、伏击、同时损失、中断与即时胜利 |
| 阵营 | 正常回合、供应耗尽、被移除关键组件、选择分支及特殊胜利 |
| 跨阵营 | 愤怒与移动 / 战损、医院与多来源移除、游侠关系等逐项场景 |
| 存档 | 在每种待选择状态保存、刷新、重启，继续后结果一致 |
| 并发 | 双标签重复提交、同一版本竞争、断线后重试、过期选择 ID |
| 隐私 | 对手手牌、牌序、支持者及隐藏标记不出现在响应 / SSE / 日志 |
| 对局 | 正式配置完整走到各类自然胜利；机器人仅用于覆盖，不代表 AI 已交付 |
| 发布 | 新旧存档可读、迁移备份、服务重启、回滚、真实浏览器及公网访问 |

规则差异优先使用原版观察样本验证。不能仅用同一份实现逻辑生成期望值再声称原规则正确。

## 7. 部署计划

### P1：保留测试服务，新增验收环境

当前服务继续使用现有地址。新版本先在独立端口和独立数据库中验收；通过 SSH 隧道访问验收环境，不要求立即申请第二个公网端口。演示账号和模拟对局不写入现有玩家数据库。

先保留 Node + SQLite + SSE 单实例架构。现有约 4 GB 内存 / 30 GB 磁盘是否满足目标并发，需要压测，不能据机器规格承诺容量。

### P2：HTTPS 与入口调整

推荐入口变为：TLS 反向代理 → Node 回环地址 3000；应用不再直接绑定外部入口端口。保留独立服务账号和最小写入目录。

当前公网 233 映射内部 80，并不自动具备公网 80 / 443。证书与入口选择：

- 若能新增公网 443 映射并提供域名，优先使用常规 `https://域名`。
- 若保留唯一公网 233，也可让内部 80 端口代理终止 TLS，对外使用 `https://域名:233`；证书验证可选 DNS-01，取决于域名 DNS 管理方式。

取得域名 / DNS 与映射信息后确定实际方案，不假定 HTTP-01 可以通过公网 80。启用 HTTPS 后同步更新 `APP_ORIGIN`、Secure Cookie 与健康检查；SSE 代理关闭缓冲。切换入口安排短维护窗口。

### P3：版本发布、迁移与回滚

- 建立 Git 版本与可追溯发布包；记录提交、包哈希、运行环境和数据库 schema 版本。
- 服务器采用 `releases/<版本>` 和 `current` 指针组织代码，数据目录独立；先把现有部署登记为基线版本。
- 发布前执行测试、数据库一致性备份、迁移兼容性检查；关闭新开局入口，处理正在进行的对局后再切换。
- 保持 `rulesetVersion`、`stateSchemaVersion` 与数据库 schema 独立。旧 lab 存档继续绑定旧规则，正式新开局才使用新规则。
- 迁移优先采用可向后兼容的增量方式。兼容性成立时才能单独回滚代码；若需要恢复数据库，必须评估发布后的新写入，不能直接用旧备份覆盖。
- 新版本依次通过验收环境、有限测试房间、正式入口；发布失败保留故障日志与可重现样本。

### P4：备份、监控与容量

- 配置 systemd timer 调用一致性备份；初始目标为每日备份及每次发布前备份，并保留明确轮转策略。
- 增加服务器之外的备份副本，目标先定为最坏丢失不超过 24 小时数据、约 60 分钟内恢复；这些是待演练目标，不是当前保证。
- 监控进程、HTTP / SSE 错误、磁盘余量、数据库与 WAL / 快照增长、备份最近成功时间和证书有效期。
- 逐级测试 5、10、20 个活跃房间，记录命令延迟、内存、CPU、磁盘和事件连接数；只按实测结果开放房间上限。
- 根据快照增长情况设计保留与压缩策略，保留当前可恢复状态及必要事件；不自动清空用户历史存档。
- 多进程需求出现后，再评估 PostgreSQL 和消息分发。SQLite 切换数据库也不能自动解决 SSE 跨实例同步问题。

| T07 | 猫 / 鹰全规则与点击式操作 | 正式双人自然结束、浏览器实测通过 |
| T08 | 验收环境、备份定时与一次发布回滚演练 | 操作记录和恢复结果可复核 |

T01 → T02 是研究前置；T04 是大部分完整规则的前置。T03、T08 可穿插进行。每个里程碑完成后更新规则覆盖表和实施记录，再决定下一批上线内容。

## 9. 排期方式与待确认输入

先执行 T01 / T02 的限时研究，再依据成功提取率、牌库效果数量及规则差异重估 M1 / M2。完整基础版和扩展应按多个迭代安排，不承诺在数天内恢复全部内容。每个阶段都以交付物和验收条件判断完成，不以代码量判断。

目前无需重复确认源码或服务器密码。后续真正影响方案的输入是：目标数字版的具体版本 / 内容范围、是否要求原版 3D 表现、正式使用的域名及端口映射、希望支持的同时在线人数。未知项先保留为明确假设，不阻塞本地研究和规则开发。
